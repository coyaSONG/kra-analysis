## Purpose / Big Picture

Preparing a new model should not depend on hand-copying its training
and held-out inputs from research files. Starting with the already
published evidence for a chronological fold, reconstruct two explicitly
different data views. The earlier view has exactly the admitted complete
earlier fields and selected unique-trio targets. The future view has its
original complete entry fields only. Neither view authorizes model
training or forecast publication.

## Context and Orientation

A chronological fold is a list of earlier development cards plus one
later, separate evaluation card. The original public digest binds a
private file listing these scopes and exact versions.
`docs/research/tools/kra_walk_forward_fold.py` verifies the saved
fold and its observed merge, including the original cutoff. Its
training side reads the preserved versioned result archive only after
checking that it cannot contain the future dates. Its future side uses
only the official entry packet. A true target is the known unordered
set of three horses from the frozen declared field.

The use boundary is independent of the numerical method:
`docs/research/tools/kra_exact_trio_ridge_fit.py` needs full fields
and exactly one known target per training field. It is not a
source-role verifier. Do not replace it or any registered model.

The `stage` command writes three role files and their hash receipt
once under `exact-trio-input-views` beside the original evaluation
intake receipt. It requires the fold proof to be available when it
starts and completion of all role files to precede the old cutoff.
A write spanning the cutoff is preserved as late, not rescued.
`replay` reconstructs the exact role views, uses the recorded local
start only as an audit time, validates the saved output digests, and
does not confer timely public evidence on the derived files.

`kra_exact_trio_fold_design.py` consumes only the verified source
fields to build the feature bytes. Its recipe fixes the same zero
base logit and normalization for both arms. For each of seven
API26 values, rank the present values in one declared field, give
ties the average zero-based position, and map that position to
`2*position/(m-1)-1` for `m >= 2`. Give a single observed value
or an absent value zero and keep each absence flag separately.
Sum these features and the unresolved-trainer flag over a trio.
Use the exact API26 manifest's verified within-field trainer identity
for the pair count. For trial arm B only, subtract the uniform
least-squares projection of those counts on the columns marking horse
inclusion, and divide by three. Exact rational arithmetic establishes
zero sum over the trios containing each given horse. A field with
three horses has zero residual by definition and the residual is
also zero at four horses. The fixed positive ridge is 1 in both
arms for this review-only recipe. No transform or hyperparameter is
learned here.

`training.json` contains only earlier features, with no result-dependent
fold digest embedded in its feature bytes. `training-targets.json`
adds the exact version, one validated candidate index per earlier
race, the earlier feature digest, and the exact weight 1 divided by
the complete training race count. `evaluation-inputs.json` contains
only the future feature view, with identical feature rules.
`fit_arguments` consumes the two training roles and constructs the
existing numerical fitter's arguments. A third file used as training,
wrong index, incomplete field or mismatched binding fails. The
inherited original race key and independent review rules do not
infer rescheduling aliases from a shared horse or venue.
